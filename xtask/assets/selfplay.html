Butterfly — what a from → to pair is worth

butterfly[stm][from][to], one i32 per cell, 8 192 cells per side to move. A quiet move that causes a beta cutoff gets min(180×depth, 1750) − 70; every quiet move tried and passed over before it gets a malus, scaled down by how late it was. The update is gravity-based, so cells drift toward ±8 192 but never past it. Piece type is not part of the index — only the two squares.

Did the two sides learn the same thing?

Both engines saw the same positions and ran the same code, but each only ever searched its own moves at the root, so their tables are built from different node samples. Each dot is one cell: white's engine on the horizontal axis, black's on the vertical. A cell both engines punished lands in the lower left; a cell they disagree about sits off the diagonal.

The continuation panel is a density map, not a scatter: the report only carries the largest cells, so both the map and the correlation beside it are computed over the full table while the games are played, and shipped as counts. Darker means more cells landed in that bucket.

Run the same configuration

The seed fixes the openings, but the games themselves are not reproducible: at a time control the search depth depends on how fast the machine ran, so the same command will play different moves. Use --games and a longer time control for numbers you want to trust, and treat a single game as an anecdote.

Reading the numbers

Both history tables use the same gravity update, entry += bonus − entry × |bonus| / MAX, which pulls a cell toward the sign of the bonus and slows it as it approaches the cap. A cell at the cap has been confirmed many times; a cell near zero was either hit rarely or hit in both directions. Move ordering reads 2 × butterfly + continuation[1 ply back] + continuation[2 plies back].

Where the counters come from

Every number on the Search tab is written through the stat! macro in src/stats.rs, which expands to nothing unless the stats feature is on. Ordinary builds, benches and SPRT matches carry no counter arithmetic at all — search-bench returns the same node count either way.
